## Part 1 — the live test

First on-device test whose timing is valid (EXP-012 brought inference to 84 ms against a
200 ms cadence, so the audio pipeline no longer stalls). 40 s captured, 186 inferences at
4.6/s against an expected 5.0/s.

**The keyword is detected.** Clear, confident firing during spoken "Sentinel", with
probabilities reaching 0.997-1.000, and genuine silence handled correctly — the 18-26 s
stretch sat at kw 0.001-0.05.

**But it fires far too often:**

| Measure | Value |
|---|---|
| Inferences predicting "keyword" | **106 / 186 = 57.0 %** |
| Frames at kw >= 0.90 (would fire) | **65 / 186 = 34.9 %** |
| Frames at kw >= 0.50 | 102 / 186 = 54.8 % |
| Offline test-set false-fire @ 0.90 | **10.7 %** |

## Part 2 — the parity check I owed

EXP-011 recorded that EXP-006's host/device parity proof had to be re-run once the feature
definition changed. It was not, and the live result is exactly what a feature mismatch
looks like. So it was run before blaming the model.

The parity firmware was **generated by transforming the EXP-012 detector source**, not
retyped, so the code path under test is the one the detector actually uses.

| Measurement | Value |
|---|---|
| max abs diff | **0.000112** |
| mean abs diff | 0.0000106 |
| correlation | **1.0000000000** |
| worst cell | frame 7, c12: host 2.369287 vs device 2.369174 |

Per-coefficient means agree to three decimals on all 13 coefficients. **Parity holds.** The
MFCC pipeline, the DCT, the 20 ms hop and the generated constants are all correct
on-device. The features are not the problem.

## The real finding: per-clip false-fire badly understates continuous operation

10.7 % measured offline vs 34.9 % observed live is not a contradiction — it is a
measurement of how different the two quantities are, and the project record has warned
since EXP-008 that they must not be conflated.

Two structural reasons, both dataset design rather than bugs:

1. **The test set contains only centred, complete words.** In continuous operation the
   model sees a fresh 1 s window every 200 ms, and most of those windows contain a
   *partial* word, a transition, or the tail of one word plus the head of the next. The
   model was never trained on any of that, so its behaviour there is undefined -- and it
   resolves the ambiguity towards "keyword" more often than not.
2. **Random-crop augmentation does not fix this.** Clips are 1.5 s with the word centred
   and crops are +/-0.25 s, so every training window still contains essentially the whole
   word. Not one training example is a half-word.

## What this does NOT change

- Detection of the keyword itself works, on-device, with valid timing.
- Latency (84 ms), memory (15,460 B arena) and feature parity are all confirmed good.
- The measured false-fire rate remains **per-clip on curated negatives**; false activations
  *per hour of continuous audio* are still unmeasured, and the live figure above is a
  40 s sample, not that metric.

## Fixes, in order of expected value

1. **Train on windows drawn from continuous audio**, including partial words. Every raw
   session WAV is saved, so this needs no new recordings: slide a 1 s window across the
   full sessions and label by overlap with a known utterance, adding the low-overlap
   windows as "unknown".
2. **Temporal smoothing (Phase 16)**: require N consecutive windows above threshold before
   firing. Isolated spikes are exactly what this suppresses, and it is the plan's own
   design. It should not be used to paper over (1).
3. **Broaden the unknown class** with Google Speech Commands -- justified by measurement
   since EXP-008 and reinforced here.

## Decision

**Do (1) first.** Smoothing applied before fixing the training distribution would hide the
defect rather than remove it, and would make the false-fire rate look better without the
model having learned anything.
